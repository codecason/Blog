#### 起因

最近用DeepSeek做一个OPD的对照实验。过去一年大模型圈继续狂飙突进，看到这个古董模型感觉又恍如隔世。

笔者微调的是deepseek-llm-7b-base模型。在之前做SFT的时候就发现它很容易出现无意义重复输出。这个现象也有其他人发现了，并且给它命名为Tail Repetition。

在早期的时候，笔者以为这个是常见的现象。而且还想到了instruct模型/coder模型本身已经做了SFT对齐训练，所以不会出现这种情况。但是后来发现即使强如GPT-5.6也可能出现无意义的解码。

而在benchmark例如ToolUse，Science上一旦问题需要有长思考的回答，它就很容易产生无边无际的循环往复，而且循环周期可以从小到大，最大可以达到一个很长的章节在无限重复。笔者觉得这个甚至可以归到周期性里了。

此外，即使是超大模型如DeepSeek-V4-Pro也无法避免这种情况，甚至于直接影响到了Harness的效果。github有云<sup><a href="https://github.com/deepseek-ai/DeepSeek-V3/issues/1550">[1]</a></sup>：

~~~markdown
我也在dsh中遇到类似问题了，但似乎在别的harness中并不太严重。目前我的做法是，直接在.dsh/AGENTS.md里增加提示词，限制模型重复，目前似乎得到了一定的缓解。提示词如下：

防循环守卫（anti-repetition-loop rules）

行动即调用：需要工具就直接给出工具调用；正文里禁止出现「我要发射 / 下面调用 / Emit / run / place it / 这是整个消息」这类自我旁白，正文只写给用户看的结论。
一条输出里同一短语或句式若已出现 2 次，立即停止生成，重写为一条干净的工具调用，不要继续往下堆。
禁止在正文里先"演练"工具内容（如把要写入的文件先贴一遍）再发调用；内容只出现在工具参数里。
若发现自己正在写「接下来我要做 X」，删掉这句话、直接做 X。
长任务拆成可独立验收的子步骤，每步把结论落盘；不重复已完成的动作，不反复切换目标。
可以让AI优化或根据你的实际使用和触发情况进行调整。
~~~

这里的方法是用了提示词进行规约。说实话这个方法真的让人摸不着头脑，只能说是类似于Prompt工程一样的玄学，能够work但是要达到完全兜底的效果是不可能的。

#### 原因与解决方法

解决方法是什么？

1：通过查找文献和询问AI，一个方法是调高温度（避免使用贪心解码）；一个方法是增加repetition_penalty。笔者都试过，发现并不能解决问题，输出结果仍然充满了冗余。

2：那么如果使用Instruct模型呢？这个是ok的。它的本意是"让模型学习在输出上的格式"，听起来很不错。实际效果确实如我们所想，利用Instruct后的模型deepseek-llm-7b-chat模型进行测试，它至少输出了正确的格式。

![image-20261010180410323](../../../../images/deepseek-repetition/github-repetition.png)

然而实际上即使经过了SFT的更大尺寸的模型仍然无法根除这个问题。在上面的网页版中的大模型大概率是DeepSeek-V4-Flash一类的模型，即使是非Pro其规模仍然至少达到了280B。

3：工程上的解决，利用一个外接的Harness实现尾部重复的检测和截断。事实上这个是行不通的，且不说用户可能本身就期望输出重复，即使忽略用户的重复需求，在我们已经发现的重复模式中，其重复的周期可能是不固定的，在输出侧要截断的长度可能达到了非常大的上界。

即使我们采用了方法2，其实也只是说明了DeepSeek的7B Base模型没有经过充分的SFT，而更大模型为什么没有规避这个问题，也并没有解释。

需要注意的是，7B模型本身是个Dense模型。而DeepSeek后续的大尺寸模型有很多架构上的区分。而很多大模型问题的根源都跟attention的性质有关。

#### 猜想

针对这个问题，笔者也在某平台发了一个帖子，因此也得到了一些有意思的猜想，例如：

```别的国模比较少听到循环问题，而其他国模的架构貌似都没有deepseek-v4-flash这么激进，像mimo、qwen、kimi都有稠密注意力层，glm虽然是稀疏注意力但也只是DSA，没有CSA/HCA降本增效得这么狠。```

这里提到的DSA，CSA，HCA正是DeepSeek演进过程用到的几种优化手段。

从 DSA 到 CSA、HCA，其结构的变化是：

DSA（DeepSeek Sparse Attention）先筛选历史 token，再计算注意力。DeepSeek-V3.2 在 MLA 上增加了一个轻量的 Lightning Indexer，给历史位置打分，每次选出 top-k 个位置对应的 KV 条目供主注意力使用，报告中的 k 为 2048。MLA 压缩的是每个位置的 KV 表示维度，DSA 减少的是每次主注意力读取的位置数。[DeepSeek-V3.2 技术报告，§2.1](https://arxiv.org/html/2512.02556v1#S2.SS1)

CSA（Compressed Sparse Attention）进一步沿序列长度压缩 KV。多个相邻 token 先通过可学习的加权聚合形成一个条目，索引器再从这些压缩条目中做 top-k 筛选。CSA 使用重叠压缩，相邻块的信息可以进入同一个条目；被选中后，主注意力直接读取聚合后的向量，不会再展开成块内每个 token 的独立 KV。[DeepSeek-V4 技术报告，§2.3.1](https://arxiv.org/html/2606.19348#S2.SS3.SSS1)

HCA（Heavily Compressed Attention）使用更大的压缩比例，采用不重叠的块，也去掉了 top-k 筛选。每次查询读取因果范围内全部已经形成的压缩条目。它保留了对历史各块的覆盖，但每个块都只有聚合后的表示。CSA 和 HCA 都额外保留滑动窗口内未压缩的 KV，用于处理近期的细粒度依赖。[DeepSeek-V4 技术报告，§2.3.2–2.3.3](https://arxiv.org/html/2606.19348#S2.SS3.SSS2)

按序列维度上的处理方式，可以把这几个结构放在一起看：

| 注意力结构 | 历史 KV 的组织方式 | 当前查询读取什么 |
| --- | --- | --- |
| DSA | 逐 token 保留 | 索引器选中的历史位置 |
| CSA | 相邻 token 压缩为条目 | 选中的压缩条目，加上局部窗口 |
| HCA | 更大范围的 token 压缩为条目 | 全部可见的压缩条目，加上局部窗口 |

V4 的 CSA 压缩率为 4，HCA 为 128；CSA 的 top-k 在 Flash 中为 512，在 Pro 中为 1024，两者的局部窗口均为 128 个 token。Flash 的前两层采用纯滑动窗口注意力，Pro 的前两层采用 HCA，后续层交错使用 CSA 和 HCA。因此，CSA、HCA 是 V4 中配合使用的两种层。[DeepSeek-V4 技术报告，§4.2.1](https://arxiv.org/html/2606.19348#S4.SS2.SSS1)

这些变化和重复输出有什么关系？笔者的猜想是：长任务需要模型持续区分「做过什么」和「还剩什么」，如果较早的任务状态在压缩表示中难以区分，或者相关条目没有被 CSA 选中，模型就可能再次生成已经完成的步骤。重复内容又进入后续上下文，可能让这种输出继续延长。目前笔者还没有实验证明或揭示它。

局部窗口也给这个猜想增加了限制：近期的重复内容仍然有未压缩的 KV，所以也许短句循环不能归因于"模型看不到刚才说过的话"，而长周期的循环也许就是这个原因。

当然，如果要设计实验判断这种架构是否放大了长周期重复，需要在相同参数规模的情况下，记录重复开始的位置、周期和上下文长度，通过压缩率、筛选数量或窗口大小做消融。

笔者会在后面想办法验证这个猜想并给出解决方案。



#### 另外一个问题

类似于重复输出的问题，如果让模型直接输出1000个1，你可能会得到无限循环的1的输出，在众多模型上都是如此。这个问题是如此容易复现以至于让人尴尬，也让笔者对大模型的局限有了一点点新的认识。
